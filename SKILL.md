# Scenario Brain v4.0 — сценарии видео Михаила Дашкиева

**Цель:** одобрение клиента с 1–2 итераций. **Сдвиг против v3:** это не «воркфлоу с инструкциями»,
а **конвейер с приёмкой на выходе** — гейты-документы задают контекст, но качество гарантируют
проверки результата: python-скрипты + агенты-аудиторы ДО показа клиенту.

## 4 принципа (выведены из реальных отказов)

1. **Инструкция ≠ гарантия.** Всё, что «нельзя никогда» (стоп-имена, фейк-цифры, «ты», вводные),
   живёт в проверке на выходе, а не только в гейте. Гейт ≤200 строк.
2. **Запись рабочих файлов — только после зелёных гейтов.** Субагенты пишут в staging
   (`.blocks-vNN/`); сборку делает скрипт, который отказывается писать при красных проверках.
3. **Слова клиента неприкосновенны и становятся регрессионными тестами.** Каждая правка — в
   `client-edits.md` (append-only) с классификацией; дословные формулировки не «улучшать».
   **Правка-ИДЕЯ («вставить/показать/найти X») = задача на артефакт или вопрос клиенту, НЕ текст
   сценария.** Приём вписывается в действии, не как мета-описание (реальный брак v11).
4. **Факт живёт в одном месте** — `facts.md` проекта, со статусом (confirmed/pending/rejected)
   и указателем на первоисточник. Цифра не из confirmed — в суфлёр не попадает.

## Референсы стиля (не путать роли)

- **Михаил Дашкиев — РЕЧЬ и TOV**: гейты проекта `avatar.md`+`tov.md` (собираются по
  `reference/gates-method.md` из шаблонов `reference/TEMPLATE-avatar.md` / `TEMPLATE-tov.md`);
  общая база — `knowledge-base/TOV-analysis.md`, `REFERENCE-VIDEOS.md`.
- **Топлес — СТРУКТУРА и удержание**: `knowledge-base/REFERENCE-TOPLES.md`, `TOPLES-VISUAL.md`.
  Приёмы Топлеса перекладываем в голос Михаила; лексику — никогда.
- **Кейсы и фактура**: банк кейсов `~/Documents/Projects/dashkiev-brain/_cases/` — первый
  источник ресёрча; транскрипты базы (`transcript_raw.txt`, конспекты) — второй;
  `summary.md` из базы — ЗАПРЕЩЁННЫЙ источник (галлюцинации). Веб — третий, с верификацией 2+.

## Карта конвейера (детали каждого этапа — в плейбуке)

| Этап | Что происходит | Гейт выхода | Плейбук |
|---|---|---|---|
| Э-1 | Выбор режима: брейншторм / сразу сценарий | выбор пользователя | `reference/pipeline/00-brainstorm.md` |
| Э0 | Инициализация сессии: скаффолд файлов-протоколов | структура создана | (ниже, «Протоколы») |
| Э1 | Бриф / discovery-интервью (+«что сквозной пример?») | критерий завершённости | `reference/pipeline/01-brief.md` |
| Э2 | Гейты avatar+tov (+сверка с эталоном, выбор структуры) | ≤200 строк, без «⚠️», **утверждение клиентом** | `reference/pipeline/02-gates.md` |
| Э3 | Ресёрч: _cases → транскрипты → веб | все факты в facts.md, ≥2 confirmed на метод-блок | `reference/pipeline/03-research.md` |
| Э4 | Сквозной пример (∥ Э3): анализ + артефакты + скринкаст-план | каждый метод-блок имеет CASE-кадр или кейс с артефактом | `reference/pipeline/04-case-through.md` |
| Э5–Э7 | Архитектура (+поля case/facts) → хуки → блоки fan-out в staging | комплектность/дубли ДО записи | `reference/pipeline/05-writing.md` |
| Э8 | **Предсдача**: preflight.py + 4 агента-аудитора | все blocker = 0, отчёт зелёный | `reference/pipeline/06-preflight.md` |
| Э9 | Ревью клиента (review.html → JSON → client-edits.md) | правки классифицированы: формулировка / идея-задача | там же |
| Э10 | Вычитка + юмор (капп регистра, повторный стоп-скан) + antislop | не хуже ai-assisted-light | там же |
| Э11 | Визуальный слой: материалы-first + CASE-кадры | чек-лист качества борда | `reference/pipeline/07-visual.md` |
| Э12 | Названия: генерация → выбор → «✅ ВЫБРАНО» | выбор пользователя | `reference/pipeline/07-visual.md` |
| Э13 | Выдача: Google Doc суфлёр + Slides опорный + storyboard | ссылки отданы | `reference/pipeline/08-delivery.md` |

Между этапами не спрашивать разрешения — стоп только на гейтах, требующих клиента/пользователя
(Э2 утверждение гейтов, Э6 выбор хука, Э9 ревью, Э12 название).

## Протоколы данных сессии (`sessions/<проект>/`)

| Файл | Что это |
|---|---|
| `project.yaml` | slug, версия сценария, этап, даты, люди, ожидания внешних входов |
| `facts.md` | единый реестр фактуры: факт / источник (путь+строки или URL+дата) / статус / ограничения подачи |
| `client-edits.md` | append-only реестр правок клиента: §S сквозные, §D дословные (неприкосновенные), поблочно; классификация «формулировка vs идея-задача» |
| `open-questions.md` | нерешённые вопросы ВНЕ гейтов (в гейтах «⚠️» запрещены) |
| `case-through/` | сквозной пример: case-brief, analysis, допресёрчи, artifacts/, screencast-plan |
| `.blocks-vNN/` | staging блоков текущей версии (fan-out пишет сюда) |
| `reports/preflight-vNN.md` | отчёт предсдачи по версии — «что проверено за клиента» |
| `STATE.md` | авто-HANDOFF: обновлять в конце каждой рабочей сессии |
| `avatar.md`, `tov.md` | гейты проекта (v-версии, бэкапы в `.blocks/`) |
| review.html, scenario-clean.md, scenario-final.md, storyboard.html и пр. | рабочие артефакты этапов |

## Правила субагентов (fan-out)

- Все субагенты — **model: sonnet** (пишущие, ресёрчеры, аудиторы). Главный цикл — контроль качества.
- 1 агент = 1 блок/факт/кластер; спека самодостаточна (только СВОЙ блок — чужие спеки в задачу не вкладывать).
- Субагенты НЕ пишут рабочие файлы — только staging; сборка через `reference/scripts/` с гейтами ДО записи.
- Ресёрч-агенты возвращают кандидатов с указателями; вердикт «confirmed» ставится только после
  сверки с первоисточником. Диагноз агента может быть верным, а фикс — вредным: первоисточник читать самому.
- Правки клиента субагентам передаются по ID из client-edits.md с типом (формулировка/идея).

## Предсдача (Э8) — коротко

1. **Скрипты** (`reference/scripts/preflight.py --project <slug>`): комплектность, дубли, стоп-слова
   (`reference/stop-words.md`), стоп-имена (`reference/stop-names.md`), вводные, интеграции, хронометраж.
2. **4 агента параллельно** по спекам `reference/agents/`: `misha-review` (эмулятор разбора клиента,
   порог 0 blocker), `fact-verifier`, `suffler-auditor`, `tov-auditor`.
3. Отчёт `reports/preflight-vNN.md`. **Клиенту не показываем, пока отчёт не зелёный.**
После каждого реального разбора клиента — пополнить реестр претензий в `misha-review.md` тем, что предсдача пропустила.

## Выдача и Google Docs — грабли

- Суфлёр в Google Doc: `templates/build_docx.py … suffler` → `gws drive files create --upload … --json '{"mimeType":"application/vnd.google-apps.document"}'`.
- `gws docs documents batchUpdate`: тело запроса через `--json`, documentId через `--params` (массив в --params стрингифицируется → 411).
- `replaceAllText` по тексту, на котором висит комментарий клиента, ОТВЯЗЫВАЕТ комментарий — проверяй якоря комментариев (`gws drive comments list`, поле `quotedFileContent`) до правок.
- Комментарии через API встают в список дока с цитатой, но без подсветки текста (ограничение Google).
- review.html: версия сценария ОБЯЗАНА входить в ключ localStorage (иначе браузер вернёт старые ответы как новые). Пересборка — `reference/scripts/rebuild_review.py vNN <blocks.json>`.

## Метрика успеха
Blocker-претензий клиента на первой сдаче: 0–2 · предсдача ловит ≥80% претензий (сверять отчёт
с фактическим разбором) · одобрение ≤2 итераций. Провал метрики → пополнить misha-review и стоп-листы.
