# Scenario Brain MVP — Сценарный скилл для видео Михаила Дашкиева

## Назначение

Система для создания сценариев видео в стиле Михаила Дашкиева через управляемый процесс.
**Два режима**, выбор на Этапе −1:
- **Режим A — Брейншторм** (материала нет): ИИ — участник штурма, ресёрчит, кидает
  направляющие, ловит штурм команды, режет на единицы идей, даёт проголосовать,
  группирует в главы → впадает в режим B.
- **Режим B — Сценарий**: **Discovery-бриф** → **Research** → Сверка с TOV → Выбор структуры → Архитектура → **Генерация хуков** → Сценарий по блокам (выдаётся в HTML-ревью на уровне единиц смысла) → Правки → Финал → **Вычитка** → **Визуальный слой (storyboard.html)** → **Название** → **Выдача документов (суфлёр → Google Doc + опорный → Google Slides, по слайду на единицу смысла, + HTML визуализация)**

**Главный принцип:** Не писать полный сценарий сразу, а вести команду по этапам.

**Версия:** 3.0 (Два режима + единицы смысла + двойная выдача + референс Топлес)

---

## Референсы стиля (два источника, не путать)

У скилла ДВА референсных канала с разными ролями:

- **Михаил Дашкиев — РЕЧЬ и TOV.** Голос, лексика, тон, обращение на «вы», манера — только
  отсюда (`knowledge-base/TOV-analysis.md`, `REFERENCE-VIDEOS.md`). Это эталон того, КАК звучит текст.
- **Топлес (Ян Топлес) — СТРУКТУРА, удержание и ВИЗУАЛ.** Как цепляет, удерживает,
  распределяет смыслы, вшивает интеграции, какие визуальные приёмы
  (`knowledge-base/REFERENCE-TOPLES.md` — структура/хуки/приёмы; `TOPLES-VISUAL.md` — визуал;
  `TOPLES-breakdowns.md` — разбор 10 роликов, сырьё). Это эталон того, КАК собрано и подано.

**Жёсткое правило:** приёмы Топлеса перекладываем в голос Михаила. Берём механику зацепа
и структуру — НЕ лексику, мат или конкретные шутки Топлеса. Если приём звучит «по-топлесовски»,
а не «по-Михаилу» — переписать под TOV Дашкиева.

**Гибрид применения референса Топлес:**
- **Всегда (baked):** на брейншторме, выборе структуры, генерации хуков и визуальном слое
  опираюсь на `REFERENCE-TOPLES.md` / `TOPLES-VISUAL.md` по умолчанию.
- **Под проект (опц.):** если пользователь даёт конкретный ролик-референс (ссылка/расшивка),
  разбираю его под текущую тему и докидываю в работу поверх baked-базы.

## Этапы работы MVP

### Этап −1: Выбор режима (первый экран)

При запуске `/scenario-brain [тема]` — ОДИН вопрос кнопкой (AskUserQuestion), до всего
остального:

- **«Брейншторм с нуля»** — материала нет, идём собирать смыслы вместе с командой
  → **режим A** (этапы A0–A4), который затем впадает в режим B.
- **«Есть материал → сразу сценарий»** — есть расшивка/запись/тезисы
  → **режим B** напрямую (Этап 0, ветка A «Лёгкий бриф»).

Это заменяет прежнее авто-ветвление по наличию материала внутри Этапа 0: выбор теперь
явный и в самом начале. Ветка B-интервью из Этапа 0 остаётся как фолбэк, если в режиме A
команда «выдохлась» и нужно дотащить пробелы вопросами.

---

## РЕЖИМ A — Брейншторм с командой (этапы A0–A4)

Запускается, если на Этапе −1 выбрано «Брейншторм с нуля». ИИ здесь — **участник
мозгоштурма**, а не анкета: сам ресёрчит, кидает направляющие идеи, ловит живой штурм
команды и структурирует его. Выход режима A = вход режима B.

**Вход — только текст.** Команда штурмит на звонке (параллельная транскрибация идёт у
них) и **вставляет текст блоками** в чат. Скилл НЕ записывает аудио и НЕ гоняет Whisper.

### Этап A0: Импульс + ресёрч

1. Беру тему, делаю быстрый ресёрч по `research-rules.md` (гейт источника сохраняется).
2. Выдаю **5–10 направляющих** одним сообщением: провокационные вопросы, неожиданные
   углы, развилки, 2–3 свежих факта/кейса с источником. Цель — не план, а импульс,
   чтобы команда начала генерить. Направляющие строю по приёмам зацепа Топлеса
   (`knowledge-base/REFERENCE-TOPLES.md` §3, §7: слом школьного мифа, парадокс-перевёртыш,
   «никто не проверял», контринтуитивные углы) — но формулирую в голосе Михаила.
3. Прошу команду штурмить и вставлять мысли блоками.

### Этап A1: Приём живого штурма

Принимаю вставленные чанки текста (по одному или пачками). Не оцениваю на лету —
накапливаю. Когда команда говорит «всё» / «достаточно» — перехожу к A2.

### Этап A2: Разбор на единицы идей

Режу ВСЁ (свои направляющие из A0 + вставленный штурм) на атомарные **единицы идей**:
одна единица = одна законченная мысль/тезис/образ/кейс. Дополняю и разворачиваю пул
(ассоциации, смежные углы) до десятков-сотни единиц. Каждая единица — короткая
формулировка (1–2 строки).

### Этап A3: Голосование по пулу идей

Собираю HTML-интерфейс голосования (общий механизм, см. «Механизм голосования» —
шаблон `templates/review-html-template.html`) в режиме `idea-pool`: список всех единиц,
по каждой — выбор **«берём / может быть / не берём»** + поле комментария. Сохраняю
`sessions/[project]/brainstorm-pool.html`, открываю `open`. Принимаю результат как JSON.

### Этап A4: Конфигурация в главы

Беру отобранные единицы (берём + спорные «может быть», помеченные пользователем) и
группирую **по смыслу** в сценарные рамки/главы. Это формирует первичный бриф +
**реестр единиц смысла** — вход в режим B. Дальше иду в режим B начиная со сверки с
эталоном (Этап 2) и далее по существующему потоку, но архитектура (Этап 4) уже опирается
на сгруппированные единицы, а не на пустую структуру.

**Выход режима A:**
- `sessions/[project]/brainstorm-pool.html` — пул идей + голоса (рабочее).
- `sessions/[project]/brief.md` — бриф, собранный из отобранных единиц.
- `sessions/[project]/units-registry.md` — реестр единиц смысла по главам (вход в режим B).

### Этап 0: Discovery-interview бриф (глубокое погружение)

**Задача:** Максимально глубоко погрузиться в контекст видео. Если у эксперта НЕТ
готовой расшивки/материалов — провести эту расшивку САМОМУ: вытащить из него весь
контент, на котором потом строится сценарий (метод, кейсы, цифры, истории, метафоры,
возражения). Цель — выйти из Этапа 0 с «синтетической расшивкой», не хуже живого
интервью с экспертом.

**Главные принципы:**
- **Адаптивность.** Следующий вопрос зависит от предыдущего ответа. Это интервью, не анкета.
- **Кнопочный выбор, а НЕ «ответь буквой/цифрой».** Для всех вопросов с вариантами
  использую инструмент **AskUserQuestion** (в Claude) — человек отвечает нажатием, а не
  печатает «A» или «1». В нём всегда есть свободный ввод («Other»), плюс можно задать
  до 4 вопросов за один экран и `multiSelect` для множественного выбора. Текстом
  спрашиваю только то, где нужен развёрнутый контент эксперта (история, кейс, как он
  объясняет) — там кнопки не подходят.
- **Глубина важнее скорости.** Лучше задать на 5 вопросов больше, чем потом писать
  сценарий «на воде». Особенно когда материалов нет.

---

#### Шаг 1. Есть ли исходный материал? (AskUserQuestion)

Первый вопрос — про наличие контента. От него зависит вся ветка:

- **Расшифровка выступления / статья / готовый текст**
- **Запись звонка / вебинара / интервью**
- **Тезисы или структура (например, таблица, план)**
- **Только идея — материала нет, надо собрать с нуля**

→ Если материал ЕСТЬ — прошу прислать/вставить, читаю, и иду по **ветке A (лёгкий бриф)**:
  добиваю только то, чего нет в материале.
→ Если материала НЕТ (или его мало) — иду по **ветке B (глубокая расшивка)**:
  провожу полноценное интервью-извлечение.

---

#### Ветка A — Лёгкий бриф (материал есть)

Материал уже даёт тему, аргументы, часть кейсов. Кнопками (AskUserQuestion) добираю
недостающее — обычно одним-двумя экранами по 3–4 вопроса:
- **Тип видео:** Обучающее · Продающее · Кейс · Мотивационное
- **Аудитория и её состояние:** кто и в какой ситуации (кнопки-типажи + Other)
- **Целевая длина:** до 10 · 15–25 · 30–45 · 60+ мин
- **Целевое действие:** скачать лид-магнит · записаться · применить самому · купить
- **Ключевая фраза:** предложить 2–3 из материала + «свой вариант»

**ОБЯЗАТЕЛЬНО: анализ пробелов расшивки перед переходом дальше.** Расшивка почти
никогда не покрывает всё — нельзя идти в Research на «воде». После чтения материала
прохожусь по чек-листу из критерия завершённости (см. ветку B) и явно отмечаю, чего
в расшивке НЕТ или мало:

- **тема + обещание** — понятно, что зритель унесёт?
- **аудитория + боль/страх** — кто это и что у них болит?
- **ядро метода** — механика/пошаговость раскрыта, а не названа?
- **доказательства** — есть конкретные кейсы (имена, компании, цифры, сроки), а не «многие клиенты»?
- **личные истории** — есть то, что нельзя нагуглить?
- **метафоры/образы** — есть, чем объяснить «на пальцах»?
- **возражения/мифы** — что развенчать?
- **эмоциональная арка** — с каким чувством входит и выходит зритель?
- **целевое действие + лид-магнит** — что сделать после и есть ли шаблон/ссылка?

По каждому НЕзакрытому пункту **задаю дополнительный вопрос** эксперту (кнопки
AskUserQuestion, где есть варианты; открытый текст, где нужен рассказ/конкретика) —
ровно как в ветке B, но точечно, только по дырам. Не выдумываю и не «дотягиваю»
недостающее сам. Если расшивка оказалась тоньше, чем ждали (закрыто меньше половины
пунктов) — перехожу к полноценному интервью ветки B.

**Не двигаюсь в Research, пока не выполнен критерий завершённости** (тема+обещание,
аудитория с болью, ядро метода, 2–3 конкретных кейса/истории, 1–2 метафоры, целевое
действие, ключевая фраза-кандидат). Сначала проговариваю эксперту, чего не хватило в
расшивке и о чём поэтому спрашиваю.

---

#### Ветка B — Глубокая расшивка (материала нет) ⭐

Провожу интервью по 12 темам. Веду по одной теме за раз; где есть варианты —
**AskUserQuestion** (кнопки), где нужен рассказ эксперта — открытый вопрос текстом с
примером ожидаемого ответа. Не вываливаю все 12 сразу — двигаюсь адаптивно.

1. **Тема и обещание** (текст): про что видео и что зритель должен унести/уметь после.
2. **Тип и цель видео** (кнопки): Обучающее · Продающее · Кейс · Мотивационное.
3. **Аудитория** (кнопки + текст): кто это, в какой ситуации, насколько «горячая»
   (новичок / в проблеме / профи). Температура трафика.
4. **Боль и страх** (текст): что у аудитории болит, чего боится, что уже пробовала и
   почему не сработало.
5. **Ядро метода** (текст): главная идея/механика. «Объясните так, будто мне впервые».
   Есть ли пошаговость (протокол/алгоритм)?
6. **Доказательства** (текст): конкретные кейсы — имена, компании, цифры, сроки.
   Просить именно конкретику, а не «многие клиенты».
7. **Личные истории** (текст): провалы и победы эксперта/клиентов — то, что нельзя
   нагуглить. Это золото для уникальности.
8. **Метафоры и образы** (текст): как эксперт обычно объясняет это «на пальцах».
   Любимые сравнения, аналогии из жизни.
9. **Возражения и мифы** (текст/кнопки): что аудитория думает неверно, какие мифы
   развенчать, на какие «а если…» ответить.
10. **Эмоциональная арка** (кнопки + текст): с каким чувством зритель входит и с каким
    должен выйти (тревога→контроль, скепсis→вера, апатия→драйв и т.п.).
11. **Формат и тон** (кнопки): длина (до 10 / 15–25 / 30–45 / 60+), тон (жёстко-прямой /
    спокойно-экспертный / вдохновляющий), «настольное» ли видео (пересылают команде?).
12. **Целевое действие и лид-магнит** (кнопки + текст): что сделать после видео,
    есть ли шаблон/чек-лист/ссылка.
+ **Ключевая фраза** (текст/кнопки): предложить 3–5 вариантов-якорей, дать выбрать.
+ **Стоп-лист** (текст): чего НЕ говорить, табу, чувствительные темы, запретные формулировки.

**Критерий завершённости ветки B:** собрано достаточно, чтобы Research только дополнял,
а не выдумывал. Минимум: тема+обещание, аудитория с болью, ядро метода, 2–3 конкретных
кейса/истории, 1–2 метафоры, целевое действие, ключевая фраза-кандидат.

---

**Полное дерево вопросов:** См. `templates/discovery-brief.md`

**Выход (для обеих веток):**
```markdown
# Итоговый бриф (из discovery-interview)

**Тип:** Обучающее (протокол)
**Тема / обещание:** Антикризисный протокол → зритель уносит порядок действий
**Аудитория:** Собственники среднего бизнеса в кризисе (температура: в проблеме)
**Боль/страх:** касса не сходится, команда ждёт решений, страх закрыться
**Ядро метода:** 2 режима → антихрупкость → деньги/расходы/выручка/штаб/FFF
**Доказательства:** [кейсы с именами и цифрами от эксперта]
**Истории:** [личные провалы/победы]
**Метафоры:** стакан/мышца, страус, переплавка
**Возражения:** «само рассосётся», «надо переждать»
**Эмоция:** тревога → контроль
**Формат:** до 40 мин, жёстко-прямой, «настольное» видео
**Действие:** скачать шаблон протокола → собрать штаб
**Ключевая фраза:** «В кризис главное — делать не всё, а главное»
**Стоп-лист:** [чего не говорить]
**Источник:** есть расшивка / собрано в интервью (ветка B)
```

**Время:** ветка A — 5–7 мин; ветка B (глубокая расшивка) — 15–25 мин, но это
экономит часы на переписывании «водянистого» сценария.

**Детали и полный список вопросов:** См. `templates/discovery-brief.md`

### Этап 1: Research (Расхождение → Схождение)

**Задача:** Обогатить сценарий конкретными кейсами, цифрами, инсайтами.

**Принцип работы:** Расхождение (широкий поиск) → Схождение (безжалостный фильтр) → Интеграция (вставка в блоки).

**Правила:** См. `research-rules.md` (антифабрикация, гейт источника, иерархия) и `references/sources.md` (курируемый реестр источников по типам тем) в корне скилла.

**Главное правило этапа: каждый факт — с проверяемым источником.** Цифра/имя/процент/кейс без источника НЕ попадает в сценарий. Устный повтор тезиса спикером ≠ источник (см. тест-кейс «горящие туры» в research-rules.md).

#### Фаза 0: Сверка с пользователем (ОБЯЗАТЕЛЬНО, до любого поиска)

Перед стартом ресёрча задаю пользователю (AskUserQuestion):
- «Собираюсь ресёрчить по темам: **[список тем из брифа]**. Точно по этим? Что добавить/убрать?»
- «Нужны отдельные источники под тему (конкретные СМИ, база данных, отчётность компании)?»

**Ресёрч не стартует без подтверждения.** Это исключает поиск «не туда» и держит live-расшивку быстрой.

#### Фаза 1: Расхождение

**Основной путь — один NotebookLM** (скилл `notebooklm`). NotebookLM отвечает ТОЛЬКО по загруженным источникам и даёт прямые ссылки — это и есть защита от выдумок.

```
notebooklm create "scenario-[project]"
notebooklm source add-research "<подтверждённый запрос>"     # собрать источники по теме
notebooklm source add <курир. URL из references/sources.md>  # докинуть проверенные источники
notebooklm ask "<вопрос по блоку>" --json                    # ответ + references[].source_id
notebooklm source fulltext <source_id>                       # точная цитата + дата
```
Из ответа берём **только** `answer` + `references[].source_id`. **Ответ без `references` под тезис = НЕ факт**, отсекаем.

> Используем ОДИН notebook. research-machine / параллельные multi-notebook прогоны НЕ запускаем.

**Фолбэк** (NotebookLM недоступен / не залогинен / 0 источников): обычный `WebSearch`/`WebFetch` + adversarial-verify (подтвердить факт в **2+ независимых источниках**; иначе пометить `⚠️ непроверено` и не использовать). Хуже текущего не будет, но гейт источника сохраняется.

**Опц. свой источник данных** (только если тема требует прямого доступа к фактуре И пользователь подтвердил на Фазе 0): подобрать готовый источник/API или собрать небольшой свой pipeline под задачу. Конкретные сервисы заранее не зашиваем — решаем под тему (приём «база/API вместо парсинга сайта»).

**Что ищем:**

### Этап 5: Генерация вариантов хука

**Задача:** Создать 5 вариантов хука (Блок 1, первые 30 секунд) — выбрать лучший → это станет началом сценария.

**Процесс:**

1. **Читаю архитектуру Блока 1:**
   - Функция: Зацепить через узнаваемую проблему

   - Аудитория (в какой ситуации)
   - Ключевая фраза

3. **Генерирую 5 вариантов хука** по 5 формулам:

**5 формул хуков:**

| Формула | Структура | Длительность | Когда использовать |
|---------|-----------|--------------|-------------------|
| 1. Вопрос-проблема | Вопрос → Усиление → Обещание | 20-25 сек | Обучающее, зритель уже в проблеме |
| 2. Шокирующий факт | Цифра → Контекст → Вопрос → Обещание | 25-30 сек | Есть впечатляющая цифра/кейс |
| 3. История-узнавание | Типичная ситуация → Последствия → "Знакомо?" → Выход | 30 сек | Зритель узнаёт себя в ситуации |
| 4. Противопоставление | Два объекта → Ситуация → Разные результаты → "В чём разница?" | 30 сек | Есть яркий контраст (успех vs провал) |
| 5. Прямое обещание | Проблема → Решение → Формат → Как использовать | 25-30 сек | Аудитория знает проблему, хочет решение |

**+ Формулы хука Топлеса** (`knowledge-base/REFERENCE-TOPLES.md` §3) — добавить к 5 базовым,
если подходят теме: «никто не проверял» + личная ставка · слом школьного мифа + антиклимакс ·
демонстрация-фокус «а что это было?» · парадокс-перевёртыш «вы думали Х — а на деле Y» ·

Все — переписать в голос Михаила (на «вы», без резкости).

**+ Реальные заходы Михаила** (`templates/hooks-module.md` §«Реальные заходы») — приоритет,
когда подходят теме: эпиграф-афоризм, парадокс-перевёртыш, концепт-метафора сразу,
трейлер-вопросы, личная исповедь, контекст-угроза, анафора-триада. Это уже его голос —
переписывать не нужно. Само-представление — ПОСЛЕ хука, не первым.

4. **Для каждого варианта пишу:**
```markdown
### Хук 1: [Формула]

**Текст:**
"[Текст хука 70-90 слов]"

**Длительность:** X секунд

**Плюсы:**
- [Что работает]

**Минусы:**
- [Что может не сработать]
```

**Критерии отбора:**
- ✅ Укладывается в 30 секунд (≈70-90 слов)
- ✅ Работает только на слух (не требует визуала для понимания)
- ✅ Обещание конкретное (не "узнаете много", а "получите 4 шага")

### Этап 7: Оценка блоков

**Задача:** Команда ставит статусы каждому блоку.

**Предусловие:** Все блоки сгенерированы и сохранены в `blocks-draft.md` (Этап 6).
Блоки НЕ показаны текстом в чате — их полный текст пользователь читает в HTML-ревью.

**ВАЖНО: блоки ВСЕГДА выдаются пользователю через HTML-артефакт** (`review.html` из
канонического шаблона `templates/review-html-template.html`), а НЕ текстом в чате. Это
единственный способ показа блоков: единый стиль у всех пользователей, удобный интерфейс
чтения и оценки, машиночитаемый вывод (JSON). Не вываливай блоки текстом и не проси
статусы текстом — всегда дай интерфейс. Шаблон править только централизованно (он общий
для всех проектов); под конкретный сценарий менять только плейсхолдеры.

**Структура единицы смысла.** Блок раскрывается как `Название → Главная мысль →
единицы смысла`. Каждая единица — атом (одна мысль/образ/кейс) с полями: `mainThought`
(относится к главной мысли блока?), `text` (формулировка), `transcript` (раскрытие,
опционально), `viz` (идея визуала, из Этапа 6), `checklist` (пункт антикризисного плана,
если единица его порождает).

**Ревью идёт по единицам, а не по блокам целиком.** В `review.html` (`MODE="review"`)
каждая единица получает голос (надо / может / не надо / переписать) + комментарий.
Сначала согласуем скелет — какие единицы вообще нужны (надо/может/не надо), потом
формулировки. При переписывании помечаю обязательные мысли, чтобы ключевое не терялось.
Чек-лист-артефакт справа набивается из полей `checklist` единиц по блокам.

**Статусы (код для ИИ ↔ подпись на русском для пользователя):**
В интерфейсе пользователь видит ТОЛЬКО русские подписи. Коды нужны для машинной обработки.
- `OK` → «Оставить как есть»
- `EDIT` → «Переписать формулировку»
- `WEAK` → «Слабый — переписать заново»
- `CUT` → «Удалить блок»
- `MOVE` → «Перенести в другое место»
- `NOT_TOV` → «Не похоже на Михаила»
- `ADD_PROOF` → «Добавить пример / факт / кейс»
- `ADD_ACTION` → «Добавить действие для зрителя»
- `TOO_LONG` → «Слишком длинно»
- `TOO_ABSTRACT` → «Слишком абстрактно»

**Процесс:**

1. **Создаю HTML-интерфейс для ревью** из `templates/review-html-template.html`:

   Заменяю плейсхолдеры:
   - `PROJECT_TITLE_PLACEHOLDER` → название проекта (в `<title>`), напр. «Антикризисный протокол»
   - `PROJECT_SUBTITLE_PLACEHOLDER` → подзаголовок, напр. «Антикризисный протокол · 11 блоков · ~40 минут»
   - `PROJECT_ID_PLACEHOLDER` → kebab-id проекта (ключ localStorage), напр. «antikrizisny-protokol»
   - `MODE_PLACEHOLDER` → `review` (ревью единиц) или `idea-pool` (голосование по идеям, режим A).
   - `BLOCKS_DATA_PLACEHOLDER` → JS-массив единиц. Формат каждой:
     ```javascript
     {n:1, t:"Хук + анонс", time:"0:00–2:30",
      key:"Ключевая фраза блока",
      text:`Полный текст ведущего. Абзацы разделять пустой строкой.
     Бэктики и доллары в тексте экранировать.`,
      viz:"идея визуала (1 строка)",
      checklist:["пункт антикризисного плана"]}
     ```
   Сохраняю в `sessions/[project]/review.html`.

   Интерфейс уже встроен в шаблон и даёт пользователю:
   - **Подсказки-онбординг** «Как пользоваться — 4 шага» + раскрываемую легенду статусов
     (чтобы даже неопытный пользователь понял, что делать).
   - На каждый блок: **выпадающий список** статусов (только русские подписи) +
     **поле подробного комментария**.
   - **Прогресс-бар** (сколько блоков оценено) + автосохранение в localStorage.
   - Кнопку **«📋 Скопировать ответы»** → копирует валидный JSON в буфер, плюс
     **«⬇ Скачать JSON»**.

2. **АВТОМАТИЧЕСКИ открываю в браузере:**
   ```bash
   open sessions/[project]/review.html
   ```

3. **Объясняю пользователю одной фразой:** прочитать блоки → выбрать статус и написать

   `block, title, status, status_ru, comment`). Парсю и перехожу к Этапу 8.
   Если пользователь всё же прислал статусы текстом — тоже принимаю, не настаиваю.

### Этап 9.5: Вычитка финала (обязательно перед выдачей)

Прохожу собранный `scenario-final.md` отдельным проходом:
1. **Орфография и грамматика** — опечатки, согласования, пунктуация. Скилл выдавал тексты
   с ошибками — этот проход обязателен, не пропускать.
2. **Корректная терминология** — общепринятые термины, не самодельные: напр.
   «твёрдые/гибкие расходы» → **«постоянные/переменные расходы»**. Сверяю доменные термины.
3. **Связность метафор** — каждая метафора (стакан/камень/пружина/страус) консистентна во
   всех блоках; если метафору убрали в одном месте — убрать ссылки на неё везде. Метафора
   не должна противоречить себе между блоками.
4. **Юмор и живость — `make-humor`** (доза из TOV). Прогоняю `scenario-final.md` через
   юмор-проход: оживляю сухие/«методичные» блоки лёгкой иронией, бытовыми метафорами,
   разговорными вставками и **инсценировкой внутреннего диалога** (мини-сценки от лица
   сопротивляющегося мозга) — в стиле Михаила. Дозу беру из оси юмора TOV
   (`knowledge-base/TOV-analysis.md`). Юмор «по-Михаилу»: самоирония, бытовые сценки,
   анекдот/культурный референс, дозированный жёсткий сленг («геморр», «пушка-бомба-огонь») —
   а НЕ каламбуры ради каламбуров. НЕ ломаю смысл, факты, цифры и структуру; фактуру не трогаю.
   Делаю ДО гейта antislop — живость даёт человеческую фактуру, которую antislop потом не сбивает.
5. **Гейт AI-слопа — `antislop`** (обязательно). Прогоняю `scenario-final.md` через детектор
   нейрослопа: сбиваю машинную структуру (триады S1, контрасты «не X, а Y» S2, лесенки S6,
   «Раньше→Сейчас» S4, вопросы-крючки S8), чищу эмодзи-декор/остаточный markdown, и слежу,
   чтобы в каждом блоке была живая фактура (цифра/имя/перволичная оговорка) — она перевешивает.
   Фактуру не трогаю. Порог: не хуже `ai-assisted-light`.

Правки вношу прямо в `scenario-final.md`. После вычитки СРАЗУ иду в Этап 10.

### Этап 10: Визуальный слой

**Задача:** Создать смысловой бриф визуализации для монтажёра.

**ВАЖНО:** Визуализируем **НЕ блоками, а смысловыми фразами**.

**Вход:** черновые `viz`-идеи, уже привязанные к единицам на Этапе 6. Этап 10 их дочищает
и достраивает (реальный артефакт-доказательство, паттерн, таймкод, b-roll), а не выдумывает
заново. Пустые `viz` — добираю здесь.

**ГЛАВНЫЙ ПРИНЦИП №1: НЕ рисуем визуал ЗА команду.** viz-идея — это всегда ТЕКСТОВОЕ
описание «что показать» (речевая идея-направление), а НЕ задание сгенерировать картинку.
Авто-генерация изображений загоняет творцов в рамки и вредит — они придумают сильнее сами.
Пример хорошей идеи: «тут показать на молекулярном уровне под микроскопом, как зарождается
фотосинтез» или «генерация: как выглядел бы мир без растений». Мы даём слова, команда решает,
как воплотить.

**ГЛАВНЫЙ ПРИНЦИП №2: ищем РЕАЛЬНЫЙ артефакт под тезис, а не рисуем абстрактную иконку.**
Под каждый кейс/факт/метафору сначала ищем реальное доказательство — кадр из фильма/сериала, мем, фото реального человека, скрин СМИ-упоминания, реальный кейс компании (источники — `references/sources.md`). Абстрактная генерация (силуэт страуса, иконка) — **крайняя мера**, когда реального артефакта под тезис не существует, а не цель по умолчанию. Особенно это касается фактов из Этапа 1: кейс из research-insights → визуал служит его **доказательством** (скрин/фото/СМИ со ссылкой), а не украшением.

**Референс визуальных приёмов — Топлес** (`knowledge-base/TOPLES-VISUAL.md`): считываемые
регистры кадра (студия / демо-рамка / реклама), реальные скрины-пруфы, цифра как образ,
предметная диорама, геймификаторы для удержания. Берём приёмы, идеи описываем текстом.

**Процесс:**

1. **Читаю финальный сценарий** и разбиваю каждый блок на **смысловые фразы** (3-10 фраз на блок):
   - Одна фраза = одна мысль/образ/метафора/кейс
   - НЕ по предложениям (одна мысль может быть 2-3 предложения)
   - Каждая фраза = кандидат на визуализацию

2. **Для каждой фразы определяю:**
   - Нужна ли визуализация? (Да, если есть триггер)
   - Триггер визуализации:
     - Метафора ("как пружина", "как страус")
     - Список ("3 шага", "4 типа")
     - Кейс компании ("Airbnb", "М.Видео")
     - Цифры/статистика ("20 млрд убытка")
     - Эмоция ("страх", "паника")
     - Концепция ("антихрупкость", "трансформация")
     - Ключевая фраза (главный месседж)
   - Матчу триггер → визуальный паттерн (из базы)

3. **Для каждой визуализируемой фразы создаю кадр:**
   - **ФРАЗА:** Текст Михаила (буквально)
   - **ТАЙМКОД:** Примерное время (0:15-0:25)
   - **ЧТО:** Описание визуала (композиция, объекты, движение)
   - **ЗАЧЕМ:** Какой смысл подчёркивает
   - **ПОЧЕМУ ЗДЕСЬ:** Как усиливает речь в этот момент
   - **ПАТТЕРН:** Код из базы (A1, B2, F5...)
   - **АНИМАЦИЯ:** Что двигается/меняется (если есть)
   - **АРТЕФАКТ (реальное доказательство):** ищем под тезис реальный объект, а не генерим. Поля:
     - **ТИП:** кадр из фильма/сериала · мем · фото реального человека/лица · скрин СМИ-упоминания · реальный кейс компании
     - **ГДЕ ИСКАТЬ:** конкретный источник (см. категорию в `references/sources.md`)
     - **ССЫЛКА-ПЕРВОИСТОЧНИК:** обязательна (URL + дата). Пусто → пометить `⚠️ источник не найден` для монтажёра, не выдавать как факт
     - **СВЯЗЬ С ФАКТОМ:** строка из `research-insights.md`, чей тезис этот артефакт доказывает (если применимо)
   - **РЕФЕРЕНС:** Концептуальное направление
   - **B-ROLL:** 3-4 варианта footage (если нужен)

**ПРАВИЛА визуализации:**

**✅ Описываю:**
- **Реальный артефакт-доказательство под тезис** (приоритет): кадр/мем/фото/скрин СМИ со ссылкой-первоисточником
- Композицию кадра (split-screen, overlay, PiP)
- Объекты и их действия (монолит трескается, пружина сжимается)
- Смысловую нагрузку (почему это работает)
- Цвета и формы (фиолетовый силуэт, белый текст на чёрном)
- Референс-направление (Kurzgesagt стиль, Netflix доки)
- **B-roll варианты** (3-4 конкретных источника footage + рекомендация)

**❌ НЕ описываю:**
- Одежду Михаила
- Причёску, аксессуары
- Детали внешнего вида
- Технические параметры анимации (keyframes, fps)
- **Абстрактные иконки там, где есть реальный артефакт** (иконка/силуэт — только если реального доказательства под тезис не существует)

**Таблица триггеров → паттернов → артефакт-кандидат:**

**После визуального слоя СРАЗУ перехожу к Этапу 11** (Генерация названий) — не спрашиваю разрешения.

**Примечание:**

Это последний содержательный этап перед выдачей документов.

**Когда запускать:** В самом конце — после финального сценария И визуального слоя.

**Процесс:**

1. Читаю финальный сценарий
2. Определяю ключевые элементы:

   - Ключевой кейс

- ✅ Не длиннее 60 символов (для превью YouTube)

### Этап 12: Выдача документов (финал — человек получает файлы)

**Задача:** Отдать результат готовыми документами в Google (по умолчанию), а не .md:
1. **Google Doc** — суфлёр (слово-в-слово, для телепромптера).
2. **Google Slides** — опорный: **каждый слайд = одна единица смысла** (см. ниже).
3. **HTML** — `storyboard.html` (визуальный слой для монтажёра, с Этапа 10).

**Принцип:** .md-файлы — рабочая кухня. Человеку на выходе отдаём документы.

> **⚠️ КЛЮЧЕВОЕ ПЕРЕОПРЕДЕЛЕНИЕ «ОПОРНОГО» (по правке клиента).**
> Опорный — это **НЕ структура и НЕ «о чём сказать»**. Опорный — это **сами смыслы**,
> которые уже есть в сценарии, разложенные послайдно: **один слайд = одна единица смысла**
> (готовая мысль из речи, сжатая, но несущая смысл, — а не тема/заголовок раздела).
> Нельзя выдавать первую фразу абзаца буллетом — это структура, а не смысл.
> **Эталон формата** (презентация Дашкиева, по слайду на мысль):
> `https://docs.google.com/presentation/d/1dLxaCfnbWrMc0Flg7CZBECepgsrwxge_5kTKvFnSlbg/edit`

**Процесс:**

1. **Чистый источник.** Из `scenario-final.md` собираю `scenario-clean.md` — только речь и
   заголовки блоков, без меты (чейнджлог, «Главная мысль», факт-чек, альт-заходы, статусы,
   карта/источники). Из него же строю Google Doc-суфлёр.

2. **Google Doc (суфлёр).** Через `gws` заливаю чистый суфлёр в Drive с конвертацией в Google
   Doc (готовый `.docx` от `templates/build_docx.py … suffler` грузится с
   `mimeType: application/vnd.google-apps.document`):
   ```bash
   gws drive files create --upload "<Проект>-суфлёр.docx" \
     --upload-content-type "application/vnd.openxmlformats-officedocument.wordprocessingml.document" \
     --json '{"name":"<Название> — суфлёр","mimeType":"application/vnd.google-apps.document"}'
   ```

3. **Единицы смыслов → `oporny-units.md`.** Прохожу сценарий блок за блоком и выписываю
   **ключевые единицы смыслов** — каждая строка = одна готовая мысль (не топик). Формат:
   `## Блок N. Название` + строки `- <мысль>`. Это и есть содержимое слайдов опорного.

4. **Google Slides (опорный).** Скриптом `templates/build_slides.py` собираю презентацию из
   `oporny-units.md`: титульный слайд + слайды по **3-4 единицы смысла** (сгруппированы
   внутри блока, сбалансированно — без слайдов с одним тезисом). Сверху каждого слайда —
   маленькая серая метка блока (знать, что за блок), тезисы — крупно (22pt) нативными
   буллетами. Так спикер сразу видит, что впереди и к чему ведёт.
   ```bash
   python3 templates/build_slides.py sessions/[project]/oporny-units.md \
     "<ВЫБРАННОЕ НАЗВАНИЕ из Этапа 11>"   # 3-й арг — тезисов на слайд (по умолч. 4)
   ```
   Тонкости `gws slides`: `presentationId` для `batchUpdate`/`get` идёт в `--params`, НЕ в
   теле; objectId ≥ 5 символов; дефолтный слайд `p` удаляю только ПОСЛЕ добавления своих.

5. **DOCX — опционально/локально.** `templates/build_docx.py … suffler|oporny` оставляем для
   быстрой локальной выдачи (`oporny` там даёт тезисы первой фразы — это запасной, не основной
   формат опорного; основной опорный = Google Slides с единицами смыслов).

6. **Итог пользователю — ссылки:**
   - Google Doc — суфлёр слово-в-слово;
   - Google Slides — опорный (единицы смыслов послайдно);
   - `storyboard.html` — блоки визуализации.

### TOV Михаила Дашкиева (стиль речи)

**✅ ИСПОЛЬЗУЙ:**

**1. Конкретные кейсы с именами и цифрами**
- "Саша Голцов, основатель всеинструментов.ru"
- "Виктор Кузнецов, партнёр Саши Кольцовой"
- "9.840 операций" (без округлений)
- "180 млрд выручки"

**2. Метафоры из физического мира**
- "пуливеризатор vs гидрорезка" (про фокус внимания)
- "кофердам у стоматолога" (про изоляцию)
- "чёрный ящик" (про бизнес-модель)

**3. Речевые конструкции**
- Вводные слова: "знаете", "понимаете", "вот"
- Повторы для усиления: "очень-очень", "прямо-прямо"
- Вопросы-промпты: "А что такое оборачиваемость?"
- Контраст: "А вот, например..."
- Обобщение: "В общем..."
- Переход: "Итак..."

**4. Прямые формулировки**
- "больные модели"
- "палим деньги"
- "шаблонное мышление"
- "пустые вложения"

**5. Структура речи**
- Короткие предложения для акцента: "Да, поэтому нам не всё равно, куда бить."
- Длинные для раскрытия: "Правильный капекс в том, что он создаёт преимущество на уровне бизнес-модели."
- Нумерация: "первое", "второе", "третье"
- Рамки в начале: "Сегодня поговорим про..."
- Итоги: "Итак, что мы узнали..."

**6. Обращение**
- **ВСЕГДА на «вы», НИКОГДА на «ты».** Все обращения к зрителю — на «вы»
  (вы, вас, вам, ваш, ваша, ваше, ваши) и глаголы во 2-м лице мн. ч.
  (смотрите, помните, возьмите, запишите). Уважительная дистанция, а не панибратство.
  Это правило жёсткое — проверять весь текст сценария на «ты/тебя/тебе/твой» и
  переводить в «вы».
- "Вы", "мы" (включающее)
- Редко "я" (только для личного опыта/кейса)

**❌ НЕ ИСПОЛЬЗУЙ:**
- "В современном мире..."
- "Важно понимать, что..."
- "Позвольте мне пояснить..."
- "Следует отметить..."
- Пассивные конструкции ("было сделано")
- Причастные обороты ("находящиеся в состоянии")
- Disclaimer-ы ("возможно, я ошибаюсь...")
- Извинения ("извините за длинное объяснение")

**❌ КЛИШЕ-УСИЛИТЕЛИ И САМОКВАЛИФИКАТОРЫ (запрещены — это ИИ-штампы):**
Не комментируй собственную речь и не навешивай на неё ярлыки «крутости/честности/важности».
Говори по делу — сама мысль должна быть сильной, без подпорок.
- "жёстко, но честно", "честно говоря", "если честно", "скажу честно", "давай честно"
- "по-взрослому", "по-взрослому надо", "взрослый заход" (как речевой ярлык)
- "самая главная мысль", "самое важное", "главное, что ты поймёшь" (анонс важности вместо самой мысли)
- "как три копейки", "проще пареной репы", "элементарно"
- "наш с тобой девиз", "наша с тобой задача" (искусственное "сближение")
- "и вот что я тебе скажу", "знаешь, что я тебе скажу", "вот тебе главная мысль"
- "это меняет всё", "которые меняют всё", "это работает" (пустое усиление)
- "не принято говорить вслух", "о чём не говорят" (ложная эксклюзивность)
- Любое представление мысли через её оценку ("сейчас будет важное/честное/жёсткое")
  вместо того, чтобы просто сказать саму мысль.

**Примеры из транскриптов:**

1. "Главное часто выглядит очень скучно и даже банально. Например, добиться маржинальности 35% или, например, сократить затраты."

2. "То есть если рубль на входе, есть 3 руб. на выходе или X на выходе в определённом цикле времени."

3. "Палим деньги на проекты, на инициативы, на задачи, которые так никогда и не будут доведены до ума."

4. "Хватаемся за всё подряд, делаем вообще не то и не так. Суетимся, перескакиваем с одного на другое, делаем это поверхностно."

## Пример использования

### 1. Запуск
```
Пользователь: Нужен сценарий видео про антикризисный протокол
```

### 2. Брифование
```
Скилл: Я понял задачу так:
Тема: Антикризисный протокол для бизнеса
Цель: Дать практический порядок действий в кризисе
Аудитория: Предприниматели в кризисе

Что нужно уточнить:
1. Какая длительность видео?
2. Какие материалы уже есть?
3. Какое действие зритель должен сделать после?
```

### 3. Сверка с TOV
```
Скилл: Рекомендую:
- Прямой тон, без сглаживаний
- Через метафору "кризис = не паника, а протокол"
- Подходящие структуры:
  1. Протокол/Checklist (7 шагов)
  2. Хаос → Диагностика → Решение
```

### 4. Выбор структуры
```
Пользователь: Берём Протокол/Checklist
```

### 5. Архитектура
```
Скилл: Архитектура:
Блок 1: Хук — через ошибку "делать вид, что ничего не происходит"
Блок 2: Главная рамка — кризис = протокол, не паника
Блок 3-9: Шаги протокола
Блок 10: Финал — призыв к действию
```

### 6. Генерация блоков
```
Скилл: [Генерирует блоки по шаблону]
```

### 7. Редактура
```
Пользователь: Блок 3 — NOT_TOV, слишком гладко
Блок 5 — ADD_PROOF, нужен кейс
Блок 7 — OK
```

### 8. Финал
```
Скилл: [Собирает финальный сценарий]
```

## Ограничения MVP

**Не входит в MVP:**
- Deep research по теме
- Конкурентный анализ
- Монтажная карта
- Визуальный слой
- Интеграции лид-магнитов
- Автоматическое обучение на правках
- YouTube-статистика

Это можно добавить в полную версию.

## Метрики качества

**Хороший сценарий:**
- ✅ Все блоки со статусом OK
- ✅ Нет ИИ-штампов
- ✅ Есть конкретные кейсы/цифры
- ✅ Финал содержит действие для зрителя
- ✅ Похоже на Михаила (проверка по TOV)

**Плохой сценарий:**
- ❌ Абстрактные рассуждения без примеров
- ❌ Канцелярит, пассивные конструкции
- ❌ Нет призыва к действию
- ❌ Не звучит как Михаил
