# Плейбук Э4: Сквозной пример / скринкаст (case-through)

**Входы:** ответ на вопрос из брифа «что будет сквозным примером и кто даст реальные
данные» (`01-brief.md`); утверждённые `avatar.md`/`tov.md` (`02-gates.md`).
**Выходы:** `sessions/[project]/case-through/` — `case-brief.md`, `analysis.md`,
допресёрчи (например `tech-stack.md`, `svyazki-research.md`), `artifacts/`,
`screencast-plan.md`.
**Гейт выхода:** каждый метод-блок архитектуры (`05-writing.md`) обязан иметь либо CASE-кадр
из сквозного примера с реальным артефактом, либо confirmed-кейс с артефактом из `facts.md`
— ни одного блока «теория без примера».

---

## Зачем этот этап

Требование Михаила из реальных разборов (см. `client-edits.md` §S22 в эталонном проекте):
«У меня тело просит примеры»; «смысл нам снимать фильм, если мы сами не умеем делать?».
Теория без реального примера в метод-блоке — blocker на приёмке (`reference/agents/misha-review.md`,
пункт 7). Сквозной пример — это несущая конструкция видео, а не декоративная вставка:
один реальный объект (компания/проект/человек), который проходит через несколько блоков
и на каждом методе получает своё продолжение — «мы применили этот шаг именно к нему,
вот что получилось».

**Закладывается в брифе, не постфактум.** `01-brief.md` требует ответ на вопрос «что будет
сквозным примером и кто даст реальные данные» ДО перехода в Research — без названного
источника данных ресёрч по кейсу невозможен.

**Собирается параллельно ресёрчу**, не после него: пока `03-research.md` качает фактуру по
темам блоков, этот трек параллельно углубляется в сам сквозной пример.

## Структура `sessions/<proj>/case-through/`

| Файл | Назначение |
|---|---|
| `case-brief.md` | Бриф кейса: кто объект, зачем ему нужен разбор/метод, какие вопросы к нему были, на чьи данные опираемся, источники (пути к отчётам/данным, даты) |
| `analysis.md` | Разбор объекта по методологии видео — по каждому шагу метода: что сделали, что получили, конкретные цифры |
| допресёрчи | Точечные файлы под специфику кейса (напр. `tech-stack.md` — техстек объекта, `svyazki-research.md` — связки/приёмы конкурентов) — по необходимости, не шаблон |
| `artifacts/` | Скачанные/собранные материалы кейса (скрины, таблицы, графики) — то, что реально покажут на экране |
| `screencast-plan.md` | Покадровый план вставок: **блок → что на экране → якорная строка суфлёра → материал** |

### `case-brief.md` — обязательные разделы
1. **Объект и зачем ему разбор** — кто это, юрлицо/масштаб/сегмент, портфельная ли компания
   фонда или внешний кейс, прямые вопросы объекта (если есть источник вопросов).
2. **Объекты анализа** — что именно разбирается (конкуренты/сегменты/метрики) с
   идентификаторами (ИНН, домен, ссылка) — чтобы каждый факт можно было адресно проверить.
3. **Источники кейса** — пути к отчётам/входным данным с датами.

### `analysis.md`
Идёт по тем же шагам, что и метод-архитектура видео (`05-writing.md`, Этап 4): под каждый
шаг метода — что сделали именно с этим объектом, какой результат, какими цифрами это
подтверждено. Это сырьё, из которого блок-райтер (`05-writing.md`) берёт «CASE-кадр» —
конкретное продолжение сквозного примера внутри блока.

### `screencast-plan.md` — покадровый план

Формат — таблица, одна строка = один кадр вставки:

```markdown
| # | Блок / таймкод | Что на экране (записать) | Строка суфлёра-якорь | Материал |
|---|---|---|---|---|
| S1 | Б6 · ~17:30 | rusprofile.ru: ввод ИНН → карточка компании, выписка | «по каждому нашли ИНН… и подняли выписку» | живой сайт |
```

**Правила записи:**
- Негатив о третьих лицах (убытки, недоимки, слабые метрики конкретных компаний) —
  **обезличенно**: имена/ИНН блюрить или заменять на «один из…», как с любым чужим кейсом
  под стоп-листом имён (`reference/stop-names.md`).
- Курсор двигать медленно, задерживаться на подсвеченной цифре ≥2 сек (монтажу нужен зум).
- Разрешение 4K, светлая тема браузера, единый масштаб (напр. 125%) — для монтажной
  склейки одним стилем.
- Закадровый текст уже вшит в суфлёр соответствующих блоков (`05-writing.md`) — на записи
  скринкаста спикер озвучивает те же строки, либо студийный звук кладётся поверх записи
  экрана на монтаже. Студия и скринкаст могут писаться раздельно, склейка — на монтаже.

## Правило для блоков архитектуры

Каждый метод-блок (`05-writing.md`, Этап 4/6) обязан иметь одно из двух:
- **CASE-кадр** — фрагмент `analysis.md`/`screencast-plan.md` по сквозному примеру,
  вписанный в текст блока как показ/разбор конкретного объекта;
- **confirmed-кейс с артефактом** из `facts.md` (`03-research.md`) — отдельный
  подтверждённый кейс со своим материалом, если сквозной пример этот шаг метода не покрывает.

Блок без ни того, ни другого — «теория без примера», blocker на предсдаче
(`06-preflight.md`, misha-review, правило 7).
