# Плейбук Э2: Гейты проекта (avatar.md + tov.md) + сверка со структурой

**Входы:** `brief.md` (утверждён); при заходе из режима A — `units-registry.md`.
**Выходы:** `sessions/[project]/avatar.md`, `sessions/[project]/tov.md` (утверждены клиентом),
`sessions/[project]/facts.md` и `sessions/[project]/open-questions.md` (заготовки),
выбранная структура видео (вход в `05-writing.md`).
**Гейт выхода:** клиент утвердил avatar.md + tov.md **ДО** написания хоть одного блока;
структура выбрана. Без утверждения — дальше не двигаемся, модель пишет по недособранному гейту.

---

## Как собрать/обновить avatar.md + tov.md под проект

Гейт пишется НЕ для презентации клиенту, а для исполнения моделью и человеком: модель по
нему пишет, редактор по нему принимает. Полная методология, доказательная база и
чек-лист приёмки — `reference/gates-method.md` (не дублировать здесь, читать целиком
перед сборкой гейтов нового проекта). Шаблоны-рыбы с готовой структурой полей —
`reference/TEMPLATE-avatar.md` и `reference/TEMPLATE-tov.md`.

**Ядро документа ≤200 строк.** Anthropic: «target under 200 lines per CLAUDE.md file» —
длинные файлы съедают контекст и хуже исполняются. Тяжёлое (банк примеров, стоп-листы,
длинные расшифровки, фактура) выносится в `reference/` и подтягивается ссылкой, а не
вклеивается в тело гейта.

**Фактура → `facts.md`, не в гейт.** Конкретные цифры/кейсы с источником и датой живут в
реестре фактуры проекта (см. `03-research.md`), не в avatar.md/tov.md — иначе гейт
протухает вместе с проектом.

**Открытые вопросы → `open-questions.md`, не в гейт.** Нерешённый пункт («уточнить у
спикера») внутри гейта — правило-призрак: модель не может ему следовать, а ощущение, что
гейт полный, ложное. Всё непроверенное — отдельным файлом, до ответа.

**Утверждение клиентом — ДО написания блоков.** Показать avatar.md + tov.md (или
`avatar.html`/`tov.html` — читаемая сборка через `reference/scripts/build_gates_html.py`)
клиенту и получить подтверждение по каждому разделу раньше, чем стартует генерация
архитектуры/хуков/блоков (`05-writing.md`). Правки клиента на этом шаге фиксируются в
`client-edits.md` (раздел A — Аватар, раздел T — TOV) с дословной цитатой — формат и
дисциплина ведения реестра описаны в `05-writing.md`.

**Сжатый порядок сборки** (детали и обоснование каждого шага — `reference/gates-method.md` §3–5):
1. Аватар: объявить тип (proto/qualitative/statistical) и источник данных первым полем →
   собрать по пяти кольцам Ревеллы (Priority Initiatives, Success Factors, Perceived
   Barriers, Buyer's Journey, Decision Criteria) с дословными цитатами → добавить JTBD
   (push/pull/anxiety/habit) → посчитать атрибуты, декоративное вырезать → порядок полей
   цели→задачи→барьеры→критерии→навык→демография последней.
2. TOV: развести источник (живая речь) и цель (жанр сценария) → задать VOICE (3–5 черт по
   6-строчному voice chart) → задать TONE по 4 осям NN/g для каждого типа блока → задать
   иерархию-тайбрейкер на случай конфликта правил → закрытые стоп-листы с заменами →
   3–5 парных примеров «так/не так» на одном входе.
3. Прогнать чек-лист приёмки (`reference/gates-method.md` §5, пункты 1–32) по готовому
   документу до показа клиенту.

### Этап 2: Сверка с эталоном Михаила

**Задача:** Определить, какой стиль и структура подходят.

**Процесс:**
1. Читаю `knowledge-base/TOV-analysis.md` (речь/голос — эталон Дашкиева)
2. Читаю `knowledge-base/STRUCTURES-analysis.md` + `knowledge-base/REFERENCE-TOPLES.md`
   (каркас выпуска §1, актуализация §2, распределение смыслов §5, удержание §6 — эталон Топлеса)
3. Определяю:
   - Рекомендованный тон (на основе TOV)
   - 2-3 подходящие структуры (из 5 архитектур)
   - Риски по стилю
   - Что точно не делать

**Выход:**
```markdown
# Сверка с эталоном Михаила

## Рекомендованный тон:
- Прямой, без сглаживаний
- Через конкретные кейсы
- Метафоры из физического мира
- [Детали из TOV]

## Подходящие структуры:

### Структура 1: [Название]
**Почему подходит:** [обоснование]
**Риски:** [возможные проблемы]

### Структура 2: [Название]
**Почему подходит:** [обоснование]
**Риски:** [возможные проблемы]

## Рекомендация:
[Какую структуру лучше выбрать и почему]

## Что точно не делать:
- ❌ [Список анти-паттернов из TOV]
```

### Этап 3: Выбор структуры

**Задача:** Команда выбирает одну из предложенных структур.

**Процесс:**
1. Показываю 2-3 структуры с обоснованием
2. Команда выбирает одну
3. Если нужно — адаптирую структуру под задачу
