# Плейбук Э5: Архитектура, хуки, блоки (написание сценария)

**Входы:** `brief.md`; утверждённые `avatar.md`+`tov.md` и выбранная структура (`02-gates.md`);
`research-insights.md`+`facts.md` (`03-research.md`); `case-through/` (`04-case-through.md`).
**Выходы:** `architecture.md`, `hooks-variants.md`, staging `sessions/[project]/.blocks-vNN/*.md`
(по одному файлу на блок — пишет fan-out), сводный `blocks-draft.md`, пополненный по ходу
`client-edits.md`.
**Гейт выхода:** архитектура и хук утверждены; ВСЕ блоки сгенерированы (полный комплект, ни
один не пропущен) и лежат в staging — готовы к `06-preflight.md` (машинные гейты + 4 агента-
аудитора ДО показа клиенту). Сборка рабочих файлов из staging делается ТОЛЬКО там, не здесь.

## Этап 4: Архитектура видео

**Задача:** Разложить выбранную структуру на блоки с функциями. Создать детальную архитектуру
в файле.

**Процесс:**

1. Беру выбранную структуру из `02-gates.md` (Этап 3).
2. Раскладываю на блоки (обычно 8–12):

```markdown
# Архитектура видео: [Название структуры]

**Выбранная структура:** [имя из 5 архитектур]
**Целевая длина:** [минуты]
**Количество блоков:** [число]

---

## Блок 1: Хук (0:00-3:00)

**Функция:** Зацепить через узнаваемую проблему

**Смысл:** [Что здесь должно быть — детальное описание]

**Что здесь (контент):**
- [Конкретные элементы: вопрос, факт, кейс]
- [Research-инсайты для вставки]
- [Ключевые цифры/имена]

**Почему зритель смотрит дальше:** [Обещание / интрига]

**Ключевая фраза:** "[фраза из хука]"

---

## Блок 2: [Название] (3:00-8:00)
...
```

3. **ОБЯЗАТЕЛЬНО сохраняю** в `sessions/[project]/architecture.md`.
4. Каждый метод-блок отмечаю полем **сквозного примера/кейса**: какой фрагмент
   `case-through/analysis.md` (`04-case-through.md`) сюда идёт, или какой `confirmed`-кейс из
   `facts.md` — без этого блок позже уйдёт как «теория без примера» (blocker, `06-preflight.md`,
   misha-review правило 7).
5. Показываю краткую структуру:
```
Архитектура готова. Файл: sessions/[project]/architecture.md

11 блоков (~55 минут):
1. Хук (3 мин) — главная ошибка
2. Главная рамка (5 мин) — кризис = протокол
...

Переходим к Этапу 5 (Генерация хуков).
```
6. **СРАЗУ перехожу к Этапу 5** — не жду ОК, не спрашиваю разрешения.

## Этап 5: Генерация вариантов хука

**Задача:** Создать 5 вариантов хука (Блок 1, первые 30 секунд) — выбрать лучший → это станет
началом сценария.

**Когда:** ПОСЛЕ архитектуры, ДО генерации остальных блоков.

**Зачем:** Хук определяет тон и энергию всего видео. Если он слабый — провалится всё видео.

**Процесс:**

1. Читаю архитектуру Блока 1: функция, смысл, обещание.
2. Читаю бриф: тип видео, аудитория, ключевая фраза.
3. Генерирую 5 вариантов хука по 5 формулам:

| Формула | Структура | Длительность | Когда использовать |
|---------|-----------|--------------|-------------------|
| 1. Вопрос-проблема | Вопрос → Усиление → Обещание | 20-25 сек | Обучающее, зритель уже в проблеме |
| 2. Шокирующий факт | Цифра → Контекст → Вопрос → Обещание | 25-30 сек | Есть впечатляющая цифра/кейс |
| 3. История-узнавание | Типичная ситуация → Последствия → "Знакомо?" → Выход | 30 сек | Зритель узнаёт себя в ситуации |
| 4. Противопоставление | Два объекта → Ситуация → Разные результаты → "В чём разница?" | 30 сек | Есть яркий контраст (успех vs провал) |
| 5. Прямое обещание | Проблема → Решение → Формат → Как использовать | 25-30 сек | Аудитория знает проблему, хочет решение |

**+ Формулы хука Топлеса** (`knowledge-base/REFERENCE-TOPLES.md` §3) — добавить к 5 базовым,
если подходят теме: «никто не проверял» + личная ставка · слом школьного мифа + антиклимакс ·
демонстрация-фокус «а что это было?» · парадокс-перевёртыш «вы думали Х — а на деле Y» ·
фейк-тема · хук-фильтр цифрой · симуляция от 2-го лица · интерактив-вызов с «конвертом».
Все — переписать в голос Михаила (на «вы», без резкости).

**+ Реальные заходы Михаила** (`templates/hooks-module.md` §«Реальные заходы») — приоритет,
когда подходят теме: эпиграф-афоризм, парадокс-перевёртыш, концепт-метафора сразу,
трейлер-вопросы, личная исповедь, контекст-угроза, анафора-триада. Это уже его голос —
переписывать не нужно. Само-представление — ПОСЛЕ хука, не первым.

4. Для каждого варианта пишу:
```markdown
### Хук 1: [Формула]

**Текст:**
"[Текст хука 70-90 слов]"

**Длительность:** X секунд

**Плюсы:**
- [Что работает]

**Минусы:**
- [Что может не сработать]
```

5. Даю рекомендацию: какой хук лучше и почему.
6. Команда выбирает 1 вариант.
7. **После выбора хука СРАЗУ перехожу к Этапу 6** (генерация блоков) — не спрашиваю «Продолжить?».

**Критерии отбора:**
- Укладывается в 30 секунд (≈70-90 слов)
- Работает только на слух (не требует визуала для понимания)
- Обещание конкретное (не «узнаете много», а «получите 4 шага»)
- Плавный переход к Блоку 2

**Выход:** `sessions/[project]/hooks-variants.md`. **Детали формул:** `templates/hooks-module.md`.

## Реестр правок — `client-edits.md` (единый формат на весь проект)

Единственный источник правды по правкам клиента. **Append-only**: записи не удаляются, только
помечаются статусом. Дословные цитаты Михаила/Руслана — **неприкосновенны**: их нельзя
«улучшать», перефразировать или откатывать без прямой новой команды. Перед любой правкой
текста блока — сверка с этим файлом обязательна.

**Формат записи:** `ID · статус · правка · дословная цитата · где применять`.
**Статусы:** 🔴 не применено · 🟡 частично · ✅ применено (с версией, например «✅ v10»).

**Разделы (префикс ID = раздел):**

| Префикс | Что | Когда заполняется |
|---|---|---|
| **S** | Сквозные правила — регрессионные, проверяются на КАЖДОЙ сборке | по мере обнаружения, на любом этапе; сверяет `06-preflight.md` (Уровень 1 скрипт + все 4 агента) |
| **D** | Дословные формулировки клиента — неприкосновенны, агентам не менять | из гейтов, звонков, ревью |
| **A** | Правки аватара | утверждение гейтов, `02-gates.md` |
| **T** | Правки TOV | утверждение гейтов, `02-gates.md` |
| **Б** | Правки по блокам, сгруппированы `### Блок N — Название (статус)` | ревью клиента, Этап 8 (`06-preflight.md`) |
| **O** | Организационное — логистика, договорённости, НЕ текст сценария | по ходу проекта |
| **H** | История — какой пакет правок применён в какой версии | после каждой сборки |

Плюс спецразделы «канона» при крупных переписываниях (например `П-17.07в` — клиент
переписал версию целиком в Google Doc, эта версия становится каноном, дальше сценарий без
его команды не трогать) и вложенная таблица «Комментарии клиента = ЗАДАЧИ» под таким
разделом, если правки пришли как комментарии в доке (см. «Интерпретация правок» ниже).

**ID стабильны и не переиспользуются** — на них ссылаются агенты: block-writer берёт только
ID своего блока (§Б), misha-review/tov-auditor/suffler-auditor сверяются с §D перед
претензией к формулировке.

**Эталон:** `sessions/konkurentnaya-razvedka/client-edits.md` — полный рабочий реестр (S1–S23,
D1–D8, A1–A9, T1–T5, Б по 15 блокам, O1–O9, канон-раздел, H).

### Интерпретация правок — критично (реальный брак v11)

Перед тем как применить правку из `client-edits.md` к тексту, определи её ТИП:

- **Правка формулировки** («заменить X на Y», «убрать Z», «переформулировать») → правишь
  текст напрямую.
- **Правка-идея / правка-материал** («вставить два креатива и сравнить», «показать
  табличку», «найти пример», «добавить кейс») → это ЗАДАЧА, не текст:
  1. Нужен артефакт — зафиксируй запрос «нужен артефакт: …» (оркестратор либо спрашивает
     клиента, либо ищет материал сам — см. сквозной пример, `04-case-through.md`).
  2. Если артефакт уже есть — впиши приём **В ДЕЙСТВИИ**, от лица спикера: «посмотрите на
     эти два креатива — какой из них сработал?.. Вот этот. Потому что…», с пометкой
     `[показ: артефакт]`.
  3. ⛔ **ЗАПРЕЩЕНО** превращать идею в мета-описание приёма («есть такой способ: показывают
     два креатива») — это ПРЯМОЙ БРАК. Зафиксированный случай: v11, §S23 — комментарий
     Руслана в Б9 «Ещё один приём: показываете два креатива…» был мета-описанием вместо
     исполнения, вырезан.

Правило записано как сквозное `S23` в `client-edits.md` и проверяется на каждой сборке
(`06-preflight.md`, Уровень 1).

## Этап 6: Генерация блоков — fan-out по `block-writer`

**Задача:** Написать текст ВСЕХ блоков с интеграцией research-инсайтов, сквозного примера и
правок клиента. Пишет НЕ главный цикл последовательно, а **параллельный fan-out**: контракт
`reference/agents/block-writer.md`.

### Правило: 1 агент = 1 блок

Каждому агенту (`model: sonnet`) — самодостаточная спека ТОЛЬКО своего блока. Урок из реальной
регрессии: **Блок 6 затёрло текстом Блока 9**, когда в промпт агента Б6 по ошибке попала спека
Б9. Чужие спеки в задачу агента не класть — ни целиком, ни фрагментом.

### Что оркестратор собирает в промпт (весь целиком)

1. **Спека своего блока**: номер, название, функция, хронометраж (слов ±10%), ключевая мысль,
   текущий текст блока (если это переписывание, не первая генерация), правки клиента ПО ЭТОМУ
   блоку из `client-edits.md` — дословно, по ID (например Б7.1, Б7.2), а не весь файл.
2. **Гейты целиком:** `avatar.md` + `tov.md`.
3. **Срез `facts.md`:** только `confirmed`-факты, назначенные этому блоку, + их ограничения
   подачи (`03-research.md`).
4. **Фрагмент `case-through/`:** какой кусок сквозного примера проходит через этот блок —
   артефакт, цифры, что на экране (`04-case-through.md`).
5. **Сквозные правила:** `client-edits.md` §S целиком (действуют на все блоки без исключения).
6. **Контекст стыков:** последний абзац предыдущего блока + первый абзац следующего — только
   для швов, НЕ для переписывания соседних блоков.

### Что агент возвращает

Строго JSON, **ничего не пишет на диск** (полный контракт — `reference/agents/block-writer.md`):

```json
{"block": N, "title": "...", "text": "полный текст блока для суфлёра — чистая речь, абзацы пустой строкой",
 "key_phrase": "...", "viz": [{"unit": "какой момент текста", "idea": "что на экране (1 строка)"}],
 "words": N,
 "checklist_self": {"vy_only": true, "no_stop_terms": true, "no_intro_words": true,
   "facts_from_registry": true, "client_edits_applied": ["Б7.1", "Б7.2"], "metaphors_spaced": true}}
```

Жёсткие правила агента (см. файл контракта целиком): цифры/имена только из переданного среза
`facts.md`; дословные формулировки клиента вставлять как есть; начинать блок с сути, не с
«Смотрите/Давайте»; заканчивать точкой смысла, не мостом-анонсом; числа цифрами, множители
словом («150 миллиардов»); если спеки не хватает — вернуть `"error"` с вопросом, не писать
текст на догадках.

### Куда пишет оркестратор

Ответ каждого агента оркестратор кладёт в **staging**, НЕ в рабочие файлы:
`sessions/[project]/.blocks-vNN/{n:02d}.md` (двузначный номер с ведущим нулём), содержимое:

```markdown
## <title>

<text>
```

Именно в этом формате его читают `reference/scripts/preflight.py` и сборочные скрипты
(`06-preflight.md`) — заголовок `##` на первой строке, дальше пустая строка и сама речь.
Рабочий `blocks-draft.md` / `scenario-final.md` собирается ТОЛЬКО из staging и ТОЛЬКО после
зелёных гейтов (`06-preflight.md`, Уровень 1) — субагенты никогда не трогают файлы, которые
увидит клиент.

### Правила интеграции research (действуют внутри спеки агента)

- Максимум 1–2 инсайта на блок.
- Адаптировать в TOV — использовать готовую адаптацию из `research-insights.md`.
- Вставлять органично, не отдельным куском.
- Цифры и имена обязательны, если они есть в срезе `facts.md`.
- Поле `viz` заполняется сразу по каждой единице текста (1 строка — что показать в этот
  момент) — это черновик-кандидат; `07-visual.md` (Этап 10) его дочищает до реального
  артефакта/паттерна/таймкода. Так идея визуала не теряется между этапами.

### Запуск и вывод

- **Все блоки — одной волной, параллельно.** Не запускать 4 из 10 и останавливаться на
  середине, не спрашивать «Продолжить?» — весь fan-out уходит сразу.
- **Не вываливаю блоки полным текстом в чат.** Пользователь читает блоки в HTML-ревью
  (`06-preflight.md`, Этап 7), не в ленте чата. В чате — только краткая сводка:
```
## ✅ Все N блоков готовы (~XX минут)

1. Хук + анонс (0:00–2:30)
2. [Название] (2:30–7:00)
...
N. Финал + CTA

Прогоняю предсдачу (машинные гейты + 4 агента-аудитора), потом открываю ревью.
```
- **Как только все блоки в staging — сразу перехожу в `06-preflight.md`** (Уровень 1 скрипты →
  Уровень 2 агенты). HTML-ревью (бывший «Этап 7») клиенту показываю только после зелёного
  отчёта предсдачи — не раньше. Не прерываться до полной генерации и зелёного отчёта.
