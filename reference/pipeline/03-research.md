# Плейбук Э3: Research (Расхождение → Схождение)

**Входы:** `brief.md` (утверждён), `avatar.md` + `tov.md` (утверждены — нужны для адаптации
фактуры в TOV), список тем ресёрча.
**Выходы:** `sessions/[project]/research-raw.md` (расхождение), `sessions/[project]/research-insights.md`
(схождение, must-have инсайты), `sessions/[project]/facts.md` (единый реестр фактуры со
статусами confirmed/pending/rejected).
**Гейт выхода:** под каждый будущий блок набрана проверенная фактура (3–5 инсайтов), каждый
факт в `facts.md` имеет статус и источник; в сценарий позже пойдут только `confirmed`.

**Задача:** Обогатить сценарий конкретными кейсами, цифрами, инсайтами.

**Принцип работы:** Расхождение (широкий поиск) → Схождение (безжалостный фильтр) → Интеграция (вставка в блоки).

**Правила:** См. `research-rules.md` (антифабрикация, гейт источника, иерархия) и `references/sources.md` (курируемый реестр источников по типам тем) в корне скилла.

**Главное правило этапа: каждый факт — с проверяемым источником.** Цифра/имя/процент/кейс без источника НЕ попадает в сценарий. Устный повтор тезиса спикером ≠ источник (см. тест-кейс «горящие туры» в research-rules.md).

## Иерархия источников (проверять по порядку, не вперемешку)

**1. Банк кейсов — первый обязательный шаг.**
`~/Documents/Projects/dashkiev-brain/_cases/` — курируемая база готовых кейсов Дашкиева.
Смотрю сюда ДО любого веб-поиска: часто нужный кейс уже разобран и проверен.

**2. Транскрипты dashkiev-brain.**
Читаю `transcript_raw.txt` конкретной встречи/эфира (полный текст) + собственные конспекты
по теме. **`summary.md` — ЗАПРЕЩЁННЫЙ источник**: он галлюцинирует (см. кейс F-R4 в
реальном `facts.md` — придуманная цифра пришла именно из summary.md, не из транскрипта).
Любой факт из базы Дашкиева проверяется вручную по `transcript_raw.txt` с указанием
страницы/таймкода, а не пересказом.

**3. NotebookLM / веб — с верификацией.**
Если тема не закрывается двумя первыми источниками — обычный ресёрч (см. «Фаза 1» ниже),
с обязательным подтверждением факта в 2+ независимых источниках.

**Каждый факт, откуда бы он ни пришёл, заводится в `facts.md`** со статусом
`confirmed` / `pending` / `rejected` (подвид `confirmed (слова клиента)` — для фактов,
подтверждённых как прямая речь Михаила без внешней проверки: в кадре подаются от первого
лица, как внешне проверенный факт — нет). Формат карточки факта:

```markdown
### F1. <короткое имя факта>
- **Статус:** confirmed | pending | rejected | confirmed (слова клиента)
- **Факт:** <что именно, с цифрами>
- **Источник:** <путь к transcript_raw.txt + страницы/таймкоды, или URL+дата, или source_id NotebookLM>
- **Проверено:** <как именно, кем, где лежит перепроверка>
- **Используется:** <блок(и) сценария>
- **Ограничения:** <что нельзя называть/как подавать — имена под стоп-листом, косвенные признаки и т.п.>
```

## Фаза 0: Сверка с пользователем (ОБЯЗАТЕЛЬНО, до любого поиска)

Перед стартом ресёрча задаю пользователю (AskUserQuestion):
- «Собираюсь ресёрчить по темам: **[список тем из брифа]**. Точно по этим? Что добавить/убрать?»
- «Нужны отдельные источники под тему (конкретные СМИ, база данных, отчётность компании)?»

**Ресёрч не стартует без подтверждения.** Это исключает поиск «не туда» и держит live-расшивку быстрой.

## Фаза 1: Расхождение

**Основной путь — один NotebookLM** (скилл `notebooklm`). NotebookLM отвечает ТОЛЬКО по загруженным источникам и даёт прямые ссылки — это и есть защита от выдумок.

```
notebooklm create "scenario-[project]"
notebooklm source add-research "<подтверждённый запрос>"     # собрать источники по теме
notebooklm source add <курир. URL из references/sources.md>  # докинуть проверенные источники
notebooklm ask "<вопрос по блоку>" --json                    # ответ + references[].source_id
notebooklm source fulltext <source_id>                       # точная цитата + дата
```
Из ответа берём **только** `answer` + `references[].source_id`. **Ответ без `references` под тезис = НЕ факт**, отсекаем.

> Используем ОДИН notebook. research-machine / параллельные multi-notebook прогоны НЕ запускаем.

**Фолбэк** (NotebookLM недоступен / не залогинен / 0 источников): обычный `WebSearch`/`WebFetch` + adversarial-verify (подтвердить факт в **2+ независимых источниках**; иначе пометить `⚠️ непроверено` и не использовать). Хуже текущего не будет, но гейт источника сохраняется.

**Опц. свой источник данных** (только если тема требует прямого доступа к фактуре И пользователь подтвердил на Фазе 0): подобрать готовый источник/API или собрать небольшой свой pipeline под задачу. Конкретные сервисы заранее не зашиваем — решаем под тему (приём «база/API вместо парсинга сайта»).

**Что ищем:**
1. **YouTube:** Конкурентные видео по теме (топ-5)
2. **Кейсы/цифры:** реальные компании, статистика — с первоисточником
3. **Концепции:** Теории, исследования, цитаты экспертов

**Фиксация:**
Создаю `sessions/[project]/research-raw.md` с разделами:
- YouTube: конкурентные видео
- Кейсы компаний (+ source_id/URL+дата)
- Концепции и теории
- Анти-паттерны (чего избегать)

**Критерий остановки:**
- Набрана фактура под все блоки (3-5 проверенных инсайтов на блок)
- Или идеи начали повторяться

## Фаза 2: Схождение (20 мин)

**Что делаем:**
1. Отбираю must-have инсайты (3-5 на каждый будущий блок)
2. Адаптирую в TOV Михаила
3. Определяю, куда вставить

**Критерии отбора must-have:**
- ✅ Конкретный кейс с именами и цифрами
- ✅ **СВЕЖЕСТЬ: кейс/статистика только за текущий или предыдущий год.** Старше —
  не берём (устаревает, «кризис четырёхлетней давности» не резонирует). Исключение —
  концепции/книги/исследования-классика (Талеб, Беннис и т.п.): для них год не важен,
  важна корректная атрибуция. Это правило — для бизнес-кейсов и статистики рынка.
- ✅ Контринтуитивная идея
- ✅ Авторитетная цитата
- ✅ Яркая метафора/аналогия
- ✅ Статистика, усиливающая аргумент

**Критерии never:**
- ❌ Банальности ("кризис — это возможность")
- ❌ Абстракции без действий
- ❌ Противоречия основному месседжу
- ❌ **Устаревшие кейсы/цифры (старше предыдущего года).** Замени на свежий аналог.
- ❌ **Сфабрикованные факты.** Каждый кейс/цифра — с проверяемым источником и датой.
  Если факт не проверен — не вставляй. (Субагенты-ресёрчеры склонны «дорисовывать»
  конкретику — перепроверяй имена/цифры/проценты вручную.)

**ГЕЙТ ИСТОЧНИКА (жёсткое правило перед записью в insights):**
Каждая цифра / имя / процент / кейс публикуется, только если у него есть один из:
`source_id` (NotebookLM) · `URL + дата` (веб, подтверждён в 2+ источниках) · ссылка на свой источник данных + дата.
Нет источника → факт НЕ записывается. **Многократный устный повтор тезиса спикером — НЕ источник** (см. тест-кейс «горящие туры»).

**Фиксация:**
Создаю `sessions/[project]/research-insights.md` с таблицей (с колонкой «Тип источника»):
```markdown
| Блок | Инсайт | Источник | Тип источника | Адаптация в TOV |
|------|--------|----------|---------------|-----------------|
| 1    | ...    | URL/id   | NotebookLM / Web-verified / свой источник / ⚠️непроверено | "Вот смотрите..." |
```
Строки с типом `⚠️непроверено` в сценарий НЕ идут — либо найти источник, либо удалить.

Параллельно каждый отобранный факт получает карточку в `facts.md` (формат — см. «Иерархия
источников» выше), со статусом. Только `confirmed` попадает дальше в блоки.

**Выход:**
```markdown
# Research Insights

## Блок 1: [Название]
### Must-have инсайт 1
**Источник:** [URL / source_id]
**Тип источника:** [NotebookLM / Web-verified / свой источник]
**Факт:** [Оригинал + дата]
**Адаптация в TOV:** [Переписано в стиле Михаила]
**Где вставить:** [Конкретное место в блоке]

[... остальные блоки]
```
