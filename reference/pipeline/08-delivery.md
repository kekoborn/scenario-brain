# Плейбук Э8: Выдача документов

**Входы:** вычитанный `scenario-final.md` (`06-preflight.md`, Этап 9.5); `storyboard.html`
(`07-visual.md`, Этап 10); `titles-variants.md` с блоком «✅ ВЫБРАНО» (`07-visual.md`, Этап 11).
**Выходы:** Google Doc — суфлёр слово-в-слово; Google Slides — опорный (по слайду на единицу
смысла); `storyboard.html` — визуальный слой для монтажёра.
**Гейт выхода:** все три ссылки отданы пользователю; ни один Google-документ не потерял привязку
комментариев клиента (проверено по якорям ДО правок).

**Принцип:** `.md`-файлы — рабочая кухня. Человеку на выходе отдаём документы, не markdown.

## Этап 12: Выдача документов (финал)

Отдаём результат готовыми документами в Google (по умолчанию), а не `.md`:
1. **Google Doc** — суфлёр (слово-в-слово, для телепромптера).
2. **Google Slides** — опорный: **каждый слайд = одна единица смысла** (см. ниже).
3. **HTML** — `storyboard.html` (визуальный слой для монтажёра, с Этапа 10).

> **⚠️ КЛЮЧЕВОЕ ПЕРЕОПРЕДЕЛЕНИЕ «ОПОРНОГО» (по правке клиента).**
> Опорный — это **НЕ структура и НЕ «о чём сказать»**. Опорный — это **сами смыслы**, которые
> уже есть в сценарии, разложенные послайдно: **один слайд = одна единица смысла** (готовая
> мысль из речи, сжатая, но несущая смысл, — а не тема/заголовок раздела). Нельзя выдавать
> первую фразу абзаца буллетом — это структура, а не смысл.
> **Эталон формата** (презентация Дашкиева, по слайду на мысль):
> `https://docs.google.com/presentation/d/1dLxaCfnbWrMc0Flg7CZBECepgsrwxge_5kTKvFnSlbg/edit`

**Процесс:**

1. **Чистый источник.** Из `scenario-final.md` собираю `scenario-clean.md` — только речь и
   заголовки блоков, без меты (чейнджлог, «Главная мысль», факт-чек, альт-заходы, статусы,
   карта/источники). Из него же строю Google Doc-суфлёр.

2. **Google Doc (суфлёр).** Через `gws` заливаю чистый суфлёр в Drive с конвертацией в Google
   Doc (готовый `.docx` от `templates/build_docx.py … suffler` грузится с `mimeType:
   application/vnd.google-apps.document`):
   ```bash
   gws drive files create --upload "<Проект>-суфлёр.docx" \
     --upload-content-type "application/vnd.openxmlformats-officedocument.wordprocessingml.document" \
     --json '{"name":"<Название> — суфлёр","mimeType":"application/vnd.google-apps.document"}'
   ```

3. **Единицы смыслов → `oporny-units.md`.** Прохожу сценарий блок за блоком и выписываю
   ключевые единицы смыслов — каждая строка = одна готовая мысль (не топик). Формат:
   `## Блок N. Название` + строки `- <мысль>`. Это и есть содержимое слайдов опорного.

4. **Google Slides (опорный).** Скриптом `templates/build_slides.py` собираю презентацию из
   `oporny-units.md`: титульный слайд + слайды по **3-4 единицы смысла** (сгруппированы внутри
   блока, сбалансированно — без слайдов с одним тезисом). Сверху каждого слайда — маленькая
   серая метка блока, тезисы — крупно (22pt) нативными буллетами.
   ```bash
   python3 templates/build_slides.py sessions/[project]/oporny-units.md \
     "<ВЫБРАННОЕ НАЗВАНИЕ из Этапа 11>"   # 3-й арг — тезисов на слайд (по умолч. 4)
   ```

5. **DOCX — опционально/локально.** `templates/build_docx.py … suffler|oporny` — для быстрой
   локальной выдачи (`oporny` там даёт тезисы первой фразы — это запасной, не основной формат
   опорного; основной опорный = Google Slides с единицами смыслов).

6. **Итог пользователю — ссылки:**
   - Google Doc — суфлёр слово-в-слово;
   - Google Slides — опорный (единицы смыслов послайдно);
   - `storyboard.html` — блоки визуализации.

## Грабли Google API

**(а) `gws docs documents batchUpdate` — тело vs идентификатор.** Тело запроса передаётся через
`--json`, `documentId` — через `--params`, НЕ в теле. Массив в `--params` стрингифицируется, и
запрос падает с `411`. Та же логика в `gws slides`: `presentationId` для `batchUpdate`/`get` —
тоже в `--params` (см. `templates/build_slides.py`); `objectId` там же должен быть ≥5 символов;
дефолтный слайд `p` удалять только ПОСЛЕ добавления своих (нельзя удалить последний слайд).

**(б) `replaceAllText` рвёт привязку комментариев.** Правка текста, на котором висит комментарий
клиента, через `replaceAllText` ОТВЯЗЫВАЕТ комментарий от текста (комментарий остаётся в доке,
но теряет якорь). Перед любой правкой текста, где есть открытые комментарии, проверить якоря:
```
gws drive comments list <fileId>
```
смотреть поле `quotedFileContent` — именно оно показывает, к какому фрагменту текста реально
привязан комментарий сейчас.

**(в) Комментарии через API — видны, но без подсветки.** Комментарии, созданные через API, в
списке комментариев дока показываются с цитатой (`quotedFileContent`) корректно, но текст в
самом документе визуально НЕ подсвечивается (ограничение Google API, не баг интеграции). Не
пытаться это починить правкой запроса — это поведение самого Google Docs API.

**(г) Версия review.html обязана попасть в ключ localStorage.** Пересборка ревью после раунда
правок:
```bash
python3 reference/scripts/rebuild_review.py vNN <blocks.json>
```
Скрипт (`reference/scripts/rebuild_review.py`) обновляет и подпись версии в шапке, и константу
`SCENARIO_VERSION`, от которой строится ключ localStorage — падает с явной ошибкой, если не
находит `SCENARIO_VERSION` в шаблоне, вместо того чтобы тихо записать половину. Без синхронного
обновления ключа браузер клиента восстановит ответы ПРОШЛОЙ версии ревью и подсунет их как
новые — уже внесённые правки выглядят так, будто их не было (подробнее — `06-preflight.md`,
Этап 8).
